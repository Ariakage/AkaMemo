# ADR-0003: Watch 录音与传输策略

- 状态：提议中
- 日期：2026-10-28
- 决策者：工程（待真机验证后由用户确认）
- 关联：`Q-001`（ADR-0004）、`Q-005`、`Q-008`、`specs/recording.md`、`specs/24h-feasibility.md`

## 背景

watchOS 对后台录音有严格限制：

- 录音必须在应用前台启动，后台只能延续已开始的音频会话；
- 音频中断后，后台自动恢复不可靠；
- `WKExtendedRuntimeSession` 最长约 1 小时，无法覆盖全天；
- `HKWorkoutSession` 可延长后台运行，但会影响 Activity 圆环并增加审核解释成本；
- Apple Watch 电池能否支撑长时间连续录音尚未实测。

因此需要明确一套 MVP 可执行的录音与传输策略，并用真机验证。

## 选项

### 录音保活

1. **前台启动 + 后台音频延续 + 分片落盘**（推荐）
   - 优点：使用公开能力，不伪装、不播放静音；审核解释清晰。
   - 缺点：中断后需用户回前台恢复；长时间运行受系统调度影响。
2. **Extended Runtime Session**
   - 优点：短时更稳定。
   - 缺点：最长 1 小时，无法覆盖全天；类型受限。
3. **HKWorkoutSession**
   - 优点：后台运行更久。
   - 缺点：影响 Activity、用户体验误导、审核风险。
4. **播放静音音频保活**
   - 优点：可能延长后台。
   - 缺点：违背隐私原则、审核风险高；明确拒绝。

### 传输

1. **WatchConnectivity `transferFile` + 应用级确认**（推荐）
   - 优点：系统提供后台文件队列；适合分片；无需自建服务。
   - 缺点：不保证实时与顺序；需要幂等与重组。
2. **实时流式上传到后端**
   - 优点：延迟低。
   - 缺点：依赖网络与后端；隐私与成本；MVP 不需要。
3. **仅依赖 iCloud 同步**
   - 优点：无自建后端。
   - 缺点：Watch 端控制力弱；确认与清理语义不清晰。

## 决定（提议）

采用：

- 录音 **必须** 由用户在前台启动；
- 使用音频后台模式延续已开始的会话；
- 60 秒或 2 MB 分片（AAC 96 kbps/声道 / 44.1 kHz / 立体声，ADR-0011），封口时原子落盘（见 ADR-0007）；
- 中断/停止/路由变化立即封口；
- 使用 `WCSession.transferFile` 传输分片；
- iPhone 校验后发送应用级确认，Watch 收到确认后再延迟清理；
- 不使用静音播放保活；
- MVP 不使用 `HKWorkoutSession`；
- 产品目标为连续 24 小时（ADR-0004）；本策略需通过 G-001 可行性门禁后才转为“已接受”。

## 后果

**正面**

- 全部使用公开能力，审核解释成本可控。
- 分片 + 幂等 + 确认机制能覆盖大部分失联/重复场景。
- 不引入后端，隐私边界清晰。

**负面**

- 中断后无法保证自动恢复，用户需要回前台操作。
- 长时间录音的稳定性与电量仍是未知数。
- WatchConnectivity 的传输时机受系统调度影响，转写可能延迟。

**必须验证**

- 真机连续 24 小时录音的电量、热量、丢失率（按 `../specs/24h-feasibility.md`）。
- 锁屏/后台/来电/Siri/蓝牙切换后的行为。
- `UIBackgroundModes` vs `WKBackgroundModes` 的正确配置。
- 传输断开、重复、重启后的最终一致性。

## 验证与转正

- 按 `specs/recording.md` 的验证矩阵与 `specs/24h-feasibility.md` 的 G-001 在真机执行。
- 若 P0 场景与 G-001 通过：把本 ADR 状态改为“已接受”，并回写实测数据。
- 若连续录音不可行：
  - 先调整产品承诺（`Q-001`）；
  - 再评估 Workout Session 或外接电源方案；
  - 任何替代方案必须新写 ADR，不得静默切换。

## 回退

- 如果 WatchConnectivity 不可靠：评估 iCloud/后端方案，但需重新做隐私评估。
- 如果 G-001 无法在 24h 内完成：按 ADR-0004 评估降码率、外接电源、Workout Session 或调整产品目标；需用户确认。
