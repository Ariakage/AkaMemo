# ADR-0011: 音频参数：立体声 96 kbps/声道 / 44.1 kHz

- 状态：已接受
- 日期：2026-10-28
- 决策者：用户
- 关联：`Q-005`、ADR-0007、ADR-0009、`../specs/recording.md`、`../specs/24h-feasibility.md`

## 背景

原录音规格为 16 kHz / 32 kbps / 单声道 / 60 秒分片，面向语音与体积优化。用户选择：

- **AAC 96 kbps**
- **44.1 kHz**

这会显著提高音质，也显著增加 24h 录音的体积、传输量与编码功耗。必须把影响写清楚，并让 G-001/G-004 用最终参数验证。

## 选项

1. **96 kbps/声道 / 44.1 kHz / 立体声（已选）**
   - 优点：音质好，保留更多环境/音乐细节与多声道，便于后期处理。
   - 缺点：立体声 24h 约 2.07 GB；Watch 存储、传输、电量压力大；ASR 需降混/重采样。
2. 32 kbps / 16 kHz
   - 优点：24h 约 346 MB；适合语音。
   - 缺点：音质一般；用户未选。
3. 48–64 kbps / 24–44.1 kHz
   - 折中；用户未选。

## 决定

1. 音频参数：
   - 容器：M4A；
   - 编码：AAC-LC；
   - 采样率：44.1 kHz；
   - 码率：**96 kbps 每声道**；
   - 声道：**立体声（2ch）默认**；多声道按硬件/API 能力启用；记录实际 `channelCount`；不得伪造多声道；
   - 保存原始多声道 AAC；录音链路不做降混/降噪（Q-006），后期处理另行；
   - 分片：60 秒或 **2 MB**，先到者；立体声 96 kbps/声道下 60 秒约 1.44 MB。
2. 体积基线（每声道 96 kbps）：
   - 单声道：43.2 MB/h，1.04 GB/24h；
   - **立体声：86.4 MB/h，2.07 GB/24h**；
   - 4ch：172.8 MB/h，4.15 GB/24h；
   - 30 天立体声约 **62 GB**。
3. G-001/G-004 必须使用最终声道数（至少立体声）验证；不得用单声道/低码率结果冒充通过。
4. 转写前降混为单声道并重采样到 16 kHz；把降混/重采样 CPU/内存计入性能预算。
5. 如果 24h 因体积/功耗失败：
   - 记录实际数据；
   - 由用户决定降码率/降采样/外接电源/调整目标；
   - 不得静默降码率。
6. Watch→iPhone 传输按 **2.07 GB/天（立体声）**评估；必须测试 WatchConnectivity 吞吐、积压与电量。
7. Q-016 需要备份：设备级 iCloud 备份会包含音频，2.07 GB/天；用户需自行管理 iCloud 空间。App 本身不上传（ADR-0009）。
8. **2026-10-28 已确认：96 kbps 指每声道**；立体声合计 192 kbps。不得再按总码率解释；体积基线保持 2.07 GB/24h。

## 后果

**正面**

- 音质明显高于语音码率，适合环境声、音乐、多人对话。
- 立体声 96 kbps/声道在 44.1 kHz 下保留多声道与较好保真度，便于后期处理。

**负面**

- 立体声 24h 约 2.07 GB，约为单声道 96 kbps 的 2 倍、32 kbps 单声道的 6 倍；Watch 存储/传输/电量压力显著增加。
- 多声道（>2）体积线性增长；Apple Watch 是否暴露多声道取决于硬件/API，不能承诺。
- 编码功耗更高，G-001 更容易失败。
- ASR 需要降混/重采样，增加 CPU。
- Q-016 已定：iCloud 备份包含音频，约 2.07 GB/天；备份配额压力大。
- 若实际只有单声道，体积减半但多声道需求不满足；若 >2 声道，体积继续线性增长。

**必须验证**

- G-001：立体声 96 kbps/声道下 24h 录音的电量、热、存储、丢失率。
- G-004：60 秒/2 MB 分片在立体声下的写入/校验/恢复。
- WatchConnectivity 2.07 GB/天传输的吞吐与积压。
- 端上转写降混/重采样后的速度/质量。

## 验证

- 真机使用立体声 96 kbps/声道 / 44.1 kHz 完整跑 G-001/G-004。
- 记录每小时体积、总时长、传输时间、电量曲线。
- 结果回写 `../specs/recording.md` 与 `../specs/24h-feasibility.md`。

## 回退

- 如果 24h 无法达成：新写 ADR 评估 64/48 kbps 或 16 kHz；由用户确认。
- 如果传输成为瓶颈：评估批量传输、仅 Wi‑Fi、分片合并/压缩；不得丢音频。
- 如果多声道不可用：至少保留立体声；若硬件只给单声道，按实际 `channelCount` 记录并更新体积基线，不得伪造。
- 如果未来改为总码率口径：新写 ADR 并更新所有体积/传输基线；当前口径为每声道。
