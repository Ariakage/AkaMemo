# 决策记录（ADR）

> 状态：活跃 · 最后更新：2026-10-28

## 为什么需要 ADR

AkaMemo 的核心风险集中在平台能力、隐私与数据格式上。这些问题一旦用错，后期改造成本极高。ADR 用来记录：

- 我们决定了什么；
- 为什么这样决定；
- 放弃了哪些选项；
- 什么条件下需要重新评估。

代码会变，决策的理由不能丢。

## 什么时候写 ADR

以下情况 **MUST** 写 ADR：

- 引入第三方依赖或模型。
- 改变音频格式、分片策略、传输机制。
- 改变数据存储/索引/迁移方案。
- 引入云端、账号、上传路径。
- 改变最低系统版本或平台架构（如加入 Workout Session）。
- 任何“很难回退”或“跨模块”的决定。

小改动、纯 UI 调整、文案修改不需要 ADR。

## 格式

文件名：`NNNN-short-kebab-title.md`，编号递增，不复用。

```markdown
# ADR-NNNN: 标题

- 状态：提议中 / 已接受 / 已拒绝 / 已取代
- 日期：YYYY-MM-DD
- 决策者：<用户/团队>
- 关联：<Q-xxx、PR、issue>

## 背景

问题、约束、为什么现在要决定。

## 选项

1. 选项 A：优点 / 缺点 / 风险
2. 选项 B：……
3. 选项 C：……

## 决定

选择了什么，边界是什么，明确不做什么。

## 后果

- 正面：
- 负面：
- 需要后续验证/补做的事项：

## 验证

如何证明这个决定有效；失败时如何回退。
```

## 如何关闭一个开放问题

1. 由用户在 issue/对话中确认结论，或由工程给出验证数据。
2. 写 ADR（或更新已有 ADR），记录选项与理由。
3. 更新受影响的文档（需求、规格、架构、隐私）。
4. 把本表状态改为 `已定`，链接 ADR。
5. 不允许在代码里“先做了再说”；未确认的假设必须留在这里。

## 状态定义

| 状态 | 含义 |
| --- | --- |
| 提议中 | 方案已写，等待验证或用户确认；不能作为最终实现依据 |
| 已接受 | 决策生效；后续变更需新 ADR 取代 |
| 已拒绝 | 明确不采用；保留理由避免重复讨论 |
| 已取代 | 被更新 ADR 取代；保留历史 |
